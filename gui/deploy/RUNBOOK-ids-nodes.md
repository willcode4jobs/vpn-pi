# Runbook — bring a Linux node into the IDS mesh

How to set up a node for the blind-relay IDS layer: a real local sensor feed,
plus (per role) the shipper, the hub relay, or the master aggregator. Builds on
the file-share deploy (`RUNBOOK.md`, `RUNBOOK-sirius.md`) — only the IDS-specific
pieces are here. Design: `docs/ids-planning/` (README + 01–05). Implementation
status: `docs/ids-planning/BUILD-STATUS.md`.

> **SELinux scope:** the Pis (polaris, vega) run Debian-based Pi OS — **no
> SELinux**; they use the systemd sandboxing already in the unit. The SELinux
> section (§8) applies only to **enforcing** nodes (sirius is x86 with SELinux
> enforcing; any RHEL/Fedora-family node). Check with `getenforce` — if it prints
> `Disabled`/not installed, skip §8.

---

## 1. Role → config (what each node runs)

| Node | Role | `GUI_IDS` | Also sets |
|---|---|---|---|
| sirius, altair | endpoint sensor | `host` | shipper → hub (`GUI_IDS_RELAY_URL`, `GUI_IDS_NODE_KEY`, `GUI_IDS_MASTER_PUBKEY`) |
| vega | hub | `host` | the relay buffer (`GUI_IDS_RELAY=1`) + ships its own feed |
| polaris | master | `mesh` | aggregator (`GUI_IDS_MASTER_KEY`, `GUI_IDS_REGISTRY`, `GUI_IDS_RELAY_URL`) + view-password |

Env reference: `docs/ids-planning/04-connectivity-and-deployment.md §3`. The
shipper + mesh source land in Step 4 — set the env now; the daemon starts using
it when that code is deployed.

## 2. Code + virtualenv

```bash
# get the code (deploy key or rsync from the Mac — see RUNBOOK-sirius.md §1)
cd ~/projects/vpn-pi/gui/backend

# sirius (Python 3.14): no cp314 wheels for the pinned deps OR pynacl — use 3.12
python3.12 -m venv .venv          # Pis: python3 -m venv .venv is fine
./.venv/bin/pip install --upgrade pip
./.venv/bin/pip install -r requirements.txt     # now includes pynacl==1.5.0
./.venv/bin/python -c "import nacl, fastapi; print('deps ok')"
```

If pip tries to **compile** pynacl/pydantic-core (cargo/gcc errors), the venv
Python has no matching wheel — rebuild with `python3.12` and reinstall.

## 3. Deploy location

- **Debian Pis (polaris, vega):** the home checkout is fine
  (`/home/billy/projects/vpn-pi`). The systemd unit's `ProtectSystem=strict` +
  `ReadWritePaths` already confine it.
- **SELinux nodes (sirius):** **do not run the venv from `/home`** — SELinux
  blocks a service exec'ing user-home content (`203/EXEC`). Deploy to a system
  path and relabel (§8):
  ```bash
  sudo mkdir -p /opt/vpn-pi
  sudo rsync -a --delete ~/projects/vpn-pi/ /opt/vpn-pi/   # or clone there
  sudo chown -R brichardt:brichardt /opt/vpn-pi
  # rebuild the venv IN PLACE under /opt (venvs hardcode their path)
  cd /opt/vpn-pi/gui/backend && python3.12 -m venv .venv && \
    ./.venv/bin/pip install -r requirements.txt
  ```

## 4. Journal read access (sensor nodes)

`HostDataSource` shells to `journalctl`. The service runs unprivileged — grant
journal read by **group**, never root:

```bash
sudo usermod -aG systemd-journal <service-user>   # billy / brichardt
# re-login or restart the service so the new group takes effect
journalctl -n1 >/dev/null && echo "journal readable"   # as the service user
```

This covers every sensor (fail2ban/auth, sshd/login, kernel/usb, boots) since
they all surface in the journal.

## 5. Keys (operator-run — never generated by tooling on your behalf)

Generate keys **on the host that owns them**; only public keys move. Use the
keygen helper (`gui/deploy/ids-keygen.py`):

```bash
sudo mkdir -p /var/lib/vpn-pi/ids && sudo chown <user>:<user> /var/lib/vpn-pi/ids

# master (polaris) ONLY — the X25519 keypair (master.key is the crown jewel)
./.venv/bin/python ../deploy/ids-keygen.py master --out /var/lib/vpn-pi/ids
#   -> writes master.key (0600) + master.pub; copy master.pub to every node

# every sensor node — its Ed25519 signer
./.venv/bin/python ../deploy/ids-keygen.py node --out /var/lib/vpn-pi/ids
#   -> writes node.key (0600); prints the verify key to register on the master
```

On the master, add each node's verify key to the registry file
(`GUI_IDS_REGISTRY`), one `wg0-addr=base64key` per line. Copy `master.pub` to
each node's `/var/lib/vpn-pi/ids/master.pub`. No private key ever leaves its host
or transits the hub.

## 6. systemd unit (per role)

Extend the node's existing `su495-gui.service` `Environment=` block. The keydir
is under the already-writable `/var/lib/vpn-pi`, so no hardening change.

```ini
# --- sensor node (sirius/altair) — local feed + shipper ---
Environment=GUI_IDS=host
Environment=GUI_IDS_NODE_KEY=/var/lib/vpn-pi/ids/node.key
Environment=GUI_IDS_MASTER_PUBKEY=/var/lib/vpn-pi/ids/master.pub
Environment=GUI_IDS_RELAY_URL=http://10.42.0.2:8787

# --- hub (vega) — also enable the relay buffer ---
Environment=GUI_IDS=host
Environment=GUI_IDS_RELAY=1

# --- master (polaris) — aggregator ---
Environment=GUI_IDS=mesh
Environment=GUI_IDS_MASTER_KEY=/var/lib/vpn-pi/ids/master.key
Environment=GUI_IDS_REGISTRY=/var/lib/vpn-pi/ids/registry
Environment=GUI_IDS_RELAY_URL=http://10.42.0.2:8787
Environment=GUI_VIEW_PASSWORD=<set-a-password>        # Step 5
```

On SELinux nodes, also point `WorkingDirectory`/`ExecStart` at `/opt/vpn-pi/...`
(not `/home/...`). Then `sudo systemctl daemon-reload && sudo systemctl restart su495-gui`.

## 7. Firewall

No new rule. The relay rides the hub's existing `8787` (already opened to wg0 by
`pi-deployment/open-gui-port.sh`, reboot-safe via `nft-gui-port.service` — see
`NFTABLES-gui-port.md`). Shippers make **outbound** connections to the hub, which
default-deny inbound does not block.

## 8. SELinux (enforcing nodes only — e.g. sirius)

The goal: let the GUI service exec its venv, run `journalctl`, read the journal,
read its keys, and (shipper/aggregator) make an outbound TCP connection to the
hub — and **nothing else**. Two tiers; do Tier 1, add Tier 2 if you want a
confined domain.

### 8.1 Why it's blocked

Under targeted policy a systemd service may not execute binaries living under a
user home (`/home`), and a non-standard port (`8787`) is not in the default
`http_port_t` set. Symptoms: `systemctl status` shows `(code=exited,
status=203/EXEC)`, or the shipper's `connect()` is denied.

### 8.2 Tier 1 — relabel so it runs (the minimum)

```bash
# 1. label the system-path deploy (executables under /opt should be exec-able)
sudo dnf install -y policycoreutils-python-utils   # provides semanage/audit2allow
sudo semanage fcontext -a -t bin_t "/opt/vpn-pi/gui/backend/.venv/bin(/.*)?"
sudo restorecon -Rv /opt/vpn-pi

# 2. allow the GUI port (bind on the hub / connect from shippers)
sudo semanage port -a -t http_port_t -p tcp 8787    # if already defined: -m instead of -a

# 3. start it and confirm
sudo systemctl restart su495-gui
systemctl status su495-gui --no-pager
```

### 8.3 Tier 2 — capture remaining denials into a policy module (the "sandbox")

The exact allows depend on the real labels on *this* node, so generate them from
actual denials rather than trusting a hand-written policy:

```bash
# run the service while collecting denials (don't disable SELinux globally —
# make just this service permissive)
sudo semanage permissive -a "$(matchpathcon -n /opt/vpn-pi/gui/backend/.venv/bin/python | sed 's/.*://;s/_t.*/_t/')" 2>/dev/null || sudo setenforce 0

sudo systemctl restart su495-gui
#   exercise it: let the shipper run, trigger a login/USB event, hit /api/ids

# build a module from what it actually needed — THEN READ THE .te BEFORE INSTALLING
sudo ausearch -m AVC -ts recent | audit2allow -m vpn_pi_gui > vpn_pi_gui.te
less vpn_pi_gui.te          # sanity-check: nothing wild, only the allows below
sudo ausearch -m AVC -ts recent | audit2allow -M vpn_pi_gui
sudo semodule -i vpn_pi_gui.pp

# back to enforcing
sudo setenforce 1   ;   sudo semanage permissive -d <domain>   # whichever you used
```

**Allows you should expect to see** (sanity-check the generated `.te` against
this list; anything beyond it deserves a second look):

- `execute` / `execute_no_trans` on the venv `python` and its `.so`s
- `execute` of `journalctl`; read of the journal (`syslogd_var_run_t`,
  `var_log_t`)
- `name_connect` to `http_port_t` tcp/8787 (shipper → hub; master → hub)
- `read`/`open` on the keydir files under `/var/lib/vpn-pi/ids`
- `write` on `/var/lib/vpn-pi/ids-relay.db` (hub only)

> Keep the module small and reviewed — a tight allow-list IS the sandbox. If
> `audit2allow` wants something broad (e.g. `domain_dontaudit`, capability
> `sys_admin`), stop and investigate; it usually means a mislabel that
> `restorecon` should fix instead.

### 8.4 Verify enforcing

```bash
getenforce                      # Enforcing
systemctl is-active su495-gui   # active
sudo ausearch -m AVC -ts recent # no new denials after exercising it
```

---

## 9. End-to-end verification

1. **Local feed:** on a sensor node, `curl -s localhost:8787/api/ids` (via SSH
   tunnel) shows real journal events; insert a USB stick / trigger a fail2ban ban
   → it appears.
2. **Relay (once Step 4 ships):** the node's shipper deposits to the hub; on the
   hub, the relay row count grows but holds only ciphertext.
3. **Aggregate:** on the master, the SSH-forwarded GUI shows the node's events,
   decrypted + attributed; a stopped node shows a sequence gap.

---

## 10. Rollback / uninstall

```bash
sudo systemctl disable --now su495-gui
sudo semodule -r vpn_pi_gui            # if Tier 2 installed
sudo semanage port -d -t http_port_t -p tcp 8787
# keys: shred the private keys if decommissioning ( shred -u node.key )
```
