# Worklog — 2026-06-05

Moved the island GUI's durable file store off polaris and onto **vega (the wg
hub)**, fixing the real problem that surfaced while trying to bring up nodes: the
file authority was on a wg *spoke*, which other nodes could only reach
spoke-to-spoke — a path that flaps. Plus the supporting hardening, scripts, and
runbooks.

## TL;DR

- **File authority moved `polaris → vega`.** vega is the hub, so every spoke
  reaches it directly. Migration verified end to end (builder → vega, 12 ms,
  uploads persist).
- **polaris** reverts to control-plane-only master (store disabled, DB kept as
  cold rollback). It stays *out* of the data path by design.
- New idempotent, reboot-safe nftables script for the GUI port; store label now
  follows the node; full set of runbooks; dev/view quickstart.
- Committed + pushed on `feat/gui-files-ids` (`feat:` code, `dox:` docs).

   for the unauthenticated GUI port. Caught and fixed a `set -e`/`pipefail` bug
   that aborted the apply helper before it added the rule.
5. **Persistence proven:** uploads hit `/var/lib/vpn-pi/island.db`, survive a
   service restart and a reboot (vs. the in-memory placeholder, which doesn't).
6. **The real problem:** the builder (a wg spoke) couldn't reliably reach polaris
   (also a spoke). `ping 10.42.0.1` flapped; `PersistentKeepalive` didn't fix it.
   Spoke-to-spoke relay in hub-and-spoke is the fragile path.
7. **Architecture decision (below):** move the file store to **vega (the hub)**,
   *not* promote polaris to a hub.
8. **Migrated** the DB polaris → vega, stood up the sqlite store on vega bound to

9. **Verified end to end:** builder → vega `200` in ~12 ms; upload from the

10. **Builder became a pure viewer:** killed its local backend. Tried a launchd
    agent for persistence → hit macOS **TCC** (repo lives under `~/Desktop`,

    Mac just browses — no Mac-side persistence needed.
11. **Decided IDS mesh-view placement** (design only — not built): aggregate on
    polaris, not vega.

## Key decisions & rationale

### Move the file store to vega (the hub), don't make polaris a hub
- Every node is configured to talk to the hub, so hosting the store on the hub
  makes it reachable by all spokes over a direct, stable path — **no wg reconfig,
  no spoke-to-spoke**.
- **Not** polaris-as-hub: a wg hub **decrypts all spoke traffic**, which would put
  the master in the data path and break the stated property *"master sees only
  control traffic, no user payload."* polaris stays a spoke / control-plane master.
- Mirror logic: **user data → off the master (on vega); security data → off the
  edge (on polaris).**

### IDS mesh view → polaris, not vega (design)
- IDS is sensitive control-plane telemetry; polaris is the hardened,
  out-of-data-path master purpose-built to collect it.
- vega is the most-exposed node (edge + hub); aggregating IDS there means a vega
  compromise blinds detection *and* leaks the alert history.
- If IDS must transit vega to reach polaris, make it a **blind relay**
  (end-to-end encrypted to polaris); ideally have **polaris pull** from nodes.
- Keep the **per-node** IDS feed local; the **mesh aggregation** is a separate
  polaris admin feature (don't re-introduce the cut daemon/mesh coupling).

### Firewall scoping for the unauthenticated GUI API
- The upload/delete API has no auth yet, so the **firewall source scope is the
  only access control**. Default to the wg subnet (`10.42.0.0/24`) — only wg peers
  hold those addresses — or `iifname "wg0"` on the hub. Never `0.0.0.0`.
